# Local pi phase runner

Requires Python **3.9 or newer** on macOS or Linux, with `ps` on PATH. Python builds without `os.waitid` (including macOS Python <3.13) use a bounded, non-reaping `ps` zombie-state probe; the producer's exit code is collected only after process-group cleanup.

`~/.pi/agent/bin/pi-phase` is an **explicit**, foreground, cooperative wrapper for heavy commands run by this user's pi sessions and subagents on this host. It does not change shell tools or start a daemon. Adopt it for builds, tests, integration runs and local CI watching; ordinary `bash` and pre-existing jobs bypass it. It is not host-wide enforcement for other users or programs.

```sh
~/.pi/agent/bin/pi-phase run --kind build --label 'solution Release' \
  --timeout 300 --queue-timeout 120 -- dotnet build My.sln -c Release -m:2
~/.pi/agent/bin/pi-phase run --kind test --label 'unit tests' \
  --timeout 300 --queue-timeout 120 -- dotnet test Tests.csproj -c Release --no-build
~/.pi/agent/bin/pi-phase status
```

Pack and restore are build phases: use `--kind build` for `dotnet pack` and `dotnet restore`. Wrap local-package scripts the same way; the dotnet shim applies inside the script:

```sh
pi-phase run --kind build --label 'local packages' --timeout 300 -- \
  bash /path/to/cratis-local-packages.sh pack-nuget <producer> <stamp>
```

Use a single *direct executable and its arguments* after `--` for each phase. Do not hide phases in shell chains/pipelines or use `| head/grep` as gate evidence; the runner streams raw output and returns the **producer's exact exit code**. One command per phase. `-m:2` above is an **explicit example**, not a silently imposed MSBuild option: choose the project's correct configuration/CI flags and parallelism yourself. Run status in a separate terminal to see kind, label, PID, cwd and elapsed time (never full command or arguments); queued/running heartbeat messages appear on the initiating terminal every ~5 seconds. Queued status lines and heartbeats end with `id=<12 hex>`. When waiters exist, status adds a final `pi-phase: slots heavy=<busy>/<slots> integration=<busy>/<slots>` line; idle output is unchanged. A noninteractive caller must keep the foreground process running until completion. If `job_start` (pi-jobs) exists, prefer it for completion notification/cancellation; otherwise run a single bounded `bash` tool call. Set the *outer caller's* timeout greater than **queue-timeout + phase timeout + ~5 seconds cleanup/startup**, so the caller does not kill the supervisor prematurely. Do not use repeated polling as an alternative.

## Compact output with a full log

Prefer `--log FILE` over shell redirects or output pipes: it overwrites FILE (creating parent directories) with the producer's full, combined stdout/stderr without streaming it to the terminal. Runner status and heartbeats remain visible. On completion, including timeout, cancellation or queue timeout, it prints the last 60 log lines followed by `pi-phase: log=<absolute path> exit=<code> lines=<count>`. The exit status is unchanged; read the full log separately when diagnosing a failure.

```sh
~/.pi/agent/bin/pi-phase run --kind test --label 'unit tests' \
  --timeout 300 --queue-timeout 120 --log .ai-work/unit-tests.log --tail 20 \
  -- dotnet test Tests.csproj -c Release --no-build
```

`--tail N` requires `--log` and a nonnegative integer; `--tail 0` prints only runner messages and the summary. Without `--log`, output and exit behaviour are unchanged.

## Capacity and timeouts

The shipped config sets heavy capacity **4** (build/test/integration); without a config file the fallback is **2**. Integration additionally occupies **1** integration permit (atomic claim, no deadlock). CI watchers take **no heavy permits**. Config is shared in `~/.pi/agent/pi-phase/config.json`, optional, for example:

```json
{"heavy_slots": 2, "integration_slots": 1}
```

### Execution policy

Every build/test gate still enters through pi-phase. It selects `direct`, `fast` or `queued` in this order: `--policy`, `PI_PHASE_POLICY`, the first matching config rule, then automatic history/default classification. `--expect-fast` remains an alias for `--policy fast`; an explicit `--policy` wins if both are present. Flag/environment choices override config, including forcing `queued` in a direct-eligible repository. Invalid environment policies fail with a diagnostic.

```sh
pi-phase run --kind build --label 'bundle' --policy direct -- npm run build
PI_PHASE_POLICY=queued pi-phase run --kind test --label 'tests' -- npm test
```

`direct` bypasses heavy/fast capacity queues but retains memory admission, nice, MSBuild caps, RSS monitoring, timeout/cancellation and ledger recording. Its per-run ownership lease is not a capacity slot. Integration phases and fingerprints recorded as container tests refuse direct admission, print a note and use queued admission (including normal container promotion). CI watcher singleton locking is unchanged. `fast` uses the existing fast permits and eligibility/budget safeguards. `queued` forces normal admission, without automatic fast selection. Running and queued `status` lines, and every ledger record, include `policy` and `source` (`flag`, `env`, `config`, `history` or `default`). Older ledger entries remain readable.

The shipped config contains ordered policy rules (Specifications, Fundamentals, and spec/Fundamentals worktree fallbacks under the Cratis root); this is the first:

```json
{"policy":[{"path":"{{REPOS_ROOT}}/cratis/Specifications*","kinds":["build","test"],"policy":"direct","max_expected_s":90}]}
```

The installer renders `{{REPOS_ROOT}}` from the configured repositories root, preserving valid JSON. Paths are case-sensitive globs (`*` also matches `/`; a leading `~` is expanded) matched against the real cwd or its main checkout path; kinds must match too. For git worktrees, `git rev-parse --git-common-dir` resolves the shared `.git` directory and its parent checkout, with a one-second timeout; failed probes and non-git cwds get no inheritance and still use cwd rules. The explicit worktree seeds also cover non-git cwds. The first matching rule wins across both paths.

A config-direct rule applies on the first run without history, capped at `max(3 × max_expected_s, 120)` seconds (default threshold 90), or the caller's shorter timeout. Overruns exit 124. Only a p90 above the rule threshold over at least three completed runs of that fingerprint in the last seven days downgrades the rule to fast, subject to normal fast safeguards (which may further fall back to queued). One slow run, even a budget overrun, never demotes the rule by itself. Explicit direct overrides retain the caller's timeout without this config budget. Nonmatching paths retain existing automatic fast/heavy behaviour.

A parent's brief may bind the execution policy or authorize a direct light check; subagents follow it instead of re-deciding policy or priority. High priority is used only when the brief grants it. Python/Node/TS unit checks, lint and small bundle builds finishing in about two minutes without Docker or .NET are light gates; the parent can authorize `--policy direct` for these so they skip the heavy queue. These are execution permissions, not permission to skip gates.

### Fast lane

Short builds/tests can bypass a busy heavy queue using separate fast permits (no heavy permit consumed). The default, even without a config key, is `"fast_lane": {"slots": 2, "max_expected_s": 90, "kinds": ["build", "test"]}`; set `"fast_lane": false` to disable it. Slots accept 1–32, the threshold accepts positive finite seconds, and kinds may contain only `build`/`test`. Integration, CI, and fingerprints recorded as container tests (even in hint mode) are never fast; a container-test fingerprint ignores `--expect-fast` with a note.

Use `run --kind build --expect-fast ... -- COMMAND` for an unknown short command. Otherwise classification needs at least three completed (passed/failed/timed-out) ledger runs in the last seven days with p90 runtime ≤ the threshold. Fingerprints use the real cwd and command with volatile version/stamp tokens normalized: `-p:Version=…`, `/p:Version=…`, `-p:PackageVersion=…`, `/p:PackageVersion=…`, `X.Y.Z-local.…`, `X.Y.Z-train.…`, and `.g<7 hex>` suffixes use stable placeholders. Ordinary commands keep their existing fingerprints. Execution still receives the raw command, and the ledger's `argvHash` still hashes raw arguments; legacy records without a fingerprint are ignored. Even a hint is ignored, with a note, when history has a slow p90. Execution holding a fast permit is capped at `max(3 × max_expected_s, 120)` seconds, or the caller's shorter timeout. A fast-eligible phase using a heavy fallback permit keeps its normal `--timeout` without the fast budget. Exceeding that cap stops the owned process group with exit 124 and a rerun note; the fingerprint stays demoted while that overrun remains in the seven-day history (so many earlier short runs cannot hide it).

**Queue order.** Waiters rank by priority class, then aged waiters FIFO, then the rest shortest-expected-first (median of recent runs: exact command, work key, command family, repository, else `default_expected_s`). A waiter ages after `min(aging_s, queue timeout / 2)` (config `queue_order`: `mode` `shortest-first`|`fifo`, `aging_s` 30–3600 default 600, `default_expected_s` default 180, `low_promote_after_s` 30–7200 default 900). A low waiter that waited past `min(low_promote_after_s, queue timeout / 2)` competes as aged normal (FIFO by enqueue time), so low cannot starve; HIGH stays separate and capped. Worst case for a low waiter: that promotion delay plus draining the work enqueued before it (high-priority work is grant-capped). `"mode": "fifo"` restores strict priority/FIFO with no promotion. `fast_lane.shape` (default true) lets a first-ever no-compile spec run use the fast lane; one overrun demotes its command family. `status` shows `expected=`, `basis=` and `order=` per waiter and ends each queued line with `id=`; queued heartbeats end with the same `id=`.

`status` groups heavy waiters by label and prints one critical-path advisory when a label has at least two waiters or a heavy phase is fourth or deeper in the queue.
With user approval, the orchestrator may time-box high priority for **that one chain** (`pi-phase grant-priority --minutes 5`), not the whole queue.
This is guidance only: it neither grants priority nor reorders existing waiters; use a consistent chain label to make the bottleneck visible.

Fast waiters use priority then the order above. If fast permits are full, they may take a heavy permit, sharing heavy priority/FIFO reservations rather than jumping older eligible heavy waiters. Memory admission, HIGH caps, nice, MSBuild shims/caps, RSS checks, verified-pass skipping and cleanup are unchanged. `status` shows `fast=<running>/<slots> queued=<n>` and marks fast phases; `wait --eta` includes fast occupancy and fallback reservations; pass `-- COMMAND` (and optionally `--expect-fast`) to classify the caller's command against the fast queue. Fast waiters/leases use separate files, invisible to old heavy-only schedulers; new schedulers account for both lanes.

### Machine-local configuration

Put machine tuning in `~/.pi/agent/pi-phase/config.local.json`, not the
installer-managed `config.json`. The local file is optional and never installed
or synced back into the checkout. Objects merge recursively (local keys win);
arrays and scalars replace the base value. Missing local files leave shipped
settings unchanged. Invalid JSON or a non-object root warns and ignores the
overlay; invalid option values use the existing validation/defaults.
For example, `{"fast_lane":{"slots":1},"rss_cap_mb":8192}` changes only those
keys, retaining the other shipped fast-lane settings. Keep this file local.
`config.local.example.json` illustrates machine tuning; copy and adjust it locally.
Local `policy` arrays replace the shipped rules, so include any shipped rules you want to retain.

### Optional performance flags

Config also accepts these keys (unknown keys are ignored and invalid values fall back to defaults, with a note, deduplicated per phase):

- `msbuild_max_cpu`: `0` (default, off), a positive integer, or `"auto"` = `max(2, (os.cpu_count() or 1) // heavy_slots)`. For build/test/integration, an executable phase-private POSIX `dotnet` shim is prepended to the child's PATH, including calls inside scripts. It finds the real executable on the original PATH, excluding the shim directory, and inserts `-m:N` immediately after the first non-option subcommand when it is `build`, `test`, `publish`, `pack`, `msbuild` or `restore`. Arguments matching `-m`, `-m:*`, `/m`, `/m:*`, `-maxcpucount*`, `/maxcpucount*` or `--maxcpucount*` (case-insensitive) disable insertion. Absolute dotnet executable paths bypass PATH and thus the cap. For `dotnet test`, assembly arguments ending in `.dll`/`.exe` bypass insertion, as does a nearest `global.json` selecting `test.runner = "Microsoft.Testing.Platform"`. The nearest config is resolved from each invocation's cwd; an unreadable/invalid runner config also leaves arguments untouched. If the shim cannot be prepared, the phase runs uncapped with one note. Startup reports a successfully installed cap; no MSBuild response files are changed.
- `container_test_detection`: `"off"`, `"hint"` (default), or `"promote"`. Test phases probe Docker no more often than every 15 seconds, with a 5-second subprocess timeout in a daemon thread that never delays or kills the phase. The first container labelled `org.testcontainers=true` created after phase start produces one integration/filter hint. Only a phase that was the sole running test/integration phase throughout the observation interval records a SHA-1 fingerprint of the real cwd and command in `state/container-tests.json`. Missing/failing Docker is ignored. `"promote"` also makes a later matching test phase atomically claim both a heavy slot and an integration permit using the existing integration admission order. A start-generation marker remembers peers that start and finish between Docker polls. Attribution is conservative: even a peer starting after container creation but before the poll suppresses recording. Other, non-pi-phase Docker activity cannot be attributed; promotion is opt-in. To forget observations while phases are idle, remove `state/container-tests.json`.
- `cold_worktree_hint`: `true` (default). Build/test phases in a Git worktree (`.git` file) without an `obj` directory within depth 3 suggest reusing a warm lane worktree. The scan skips `.git`, `node_modules` and symlinks and stops after 1000 entries; incomplete scans produce no hint. Message only.
- `skip_passed_integration`: `false` (default). Set `true` to allow exact passed-state skipping for integration phases; container runs can depend on external state.
- `max_high`: integer 1–10 (default **3**). Caps queued plus running HIGH phases. With a valid grant, requests above the cap queue as normal without consuming a grant use and print `pi-phase: high-priority cap (3) reached; queued as normal` (using the configured cap). `status` shows `high=<n>/<cap>`.
- `phase_nice`: `0` (default, off) or an integer 1–19. Build, test and integration producers start at that Unix nice level (a caller that is already nicer keeps its level). Children inherit it, including a compiler server (VBCSCompiler) or MSBuild nodes a phase starts, so Docker, agents and health checks keep CPU when compiles saturate the host. CI watchers are unaffected. Running phases keep their priority after a config change.
- `host_pressure`: `{"mode": "off"}` by default; `off`, `observe` or `enforce`, plus `max_pressure_level` (2), `max_compressor_percent` (30), `max_swap_growth_mb_per_min` (256) and `sample_ttl_s` (5), each used when omitted. macOS only: one `sysctl -n vm.swapusage vm.compressor_bytes_used hw.memsize kern.memorystatus_vm_pressure_level kern.memorystatus_level` (1 s limit) is shared by all waiters through `state/host-sample.json` (atomic replace; a missing or corrupt file means probe again) together with a 10-minute swap history. A hold needs pressure level >= max, compressor bytes / memsize >= max percent, or swap growth (newest minus oldest sample, at least 60 s apart) >= max. `enforce` holds like `memory_admission` (wait reason `memory`; only while another phase runs, so an idle host starts one phase); `observe` never holds, sets `wouldHold` and adds `waitWouldHold` seconds (by `host`/`cpu`) to the ledger wait fields, and `wouldHoldAtAdmit` when a phase was admitted on a scan that would have held. Ledger `host` gains `pl`, `cmpPct`, `swapMb` and `swapGrowth` from the cache (never probing). Probes run outside the coordinator lock and fail open. Invalid values warn and use `off`.
- `cpu_budget`: `{"mode": "off"}` by default; `off`, `observe` or `enforce`, plus `max_units` (`"auto"` = round(1.5 x CPUs), or an integer >= 1), `costs` (`{"heavy": "msbuild", "fast": 1, "direct": 1, "integration": 2}`; `"msbuild"` = `msbuild_max_cpu`, or 2 when that is 0/auto) and `max_load_per_core` (4.0, one-minute load). Every policy, direct and fast included, takes part: a candidate is held when the units of live heavy-/fast-/direct-/integration- leases plus its own cost exceed `max_units`, or when load per core is above the limit, but only while another phase runs; `ci` is never held. `enforce` reports wait reason `cpu` (added to `waitBreakdown`/`waitScans` only when it occurs); `observe` never holds and reports `wouldHold` `cpu:<units>/<max>`. While enabled, each scan snapshots lease metadata outside the coordinator lock, as `memory_admission` does when it holds.
- `hang_timeout`: `{"mode": "off"}` by default; `{"mode": "on", "seconds": 150, "kinds": ["test"], "paths": ["<glob>", ...]}` appends `--blame-hang-timeout <seconds>s --blame-hang-dump-type none` at the runsettings boundary (the same place as the dump-type injection, after it saw your argv). It applies only to a direct `dotnet test` argv (through `env`/`nice`; never shell strings or scripts, so Tier 1 gates keep CI's timeouts), kinds `test` (never integration or ci), an empty `paths` list meaning every path, `seconds` <= `--timeout` - 30, no `--blame*`/`--hangdump*`/`--testing-platform`/`--diagnose-hang`/`--vstest-hang-minutes`/`--no-hang-timeout`, and a VSTest runner (a nearest `global.json` with `test.runner` `Microsoft.Testing.Platform` skips with a note). The ledger records `hangTimeoutS`; `argvHash` keeps the original argv. `--no-hang-timeout` opts out per run.
- `reap_build_servers`: `{"mode": "off"}` by default; `observe` (log `would reap`) or `enforce` (SIGTERM), plus `idle_s` (600), `min_age_s` (900) and `max_cpu_ms_per_min` (200). Read by `agent/bin/reap-build-servers`, which `docker-guardian` runs. It only considers the current user's orphaned (ppid 1) VBCSCompiler and `/nodeReuse:true` MSBuild nodes from a dotnet `sdk/` directory, skips phase-owned servers, resets the idle timer on any busier pass or pid/start-time change, re-reads and revalidates the pid right before each signal, never uses SIGKILL and takes no coordinator lock.
- Shared compilation stays off unless you set `PI_PHASE_SHARED_COMPILATION=1`. Then each phase exports a phase-specific `SharedCompilationId` (`pi-phase-<token>`; one already in the environment is kept and never cleaned up) so concurrent worktrees do not share one server, and after the phase's process group is gone it SIGTERMs only the same-user `VBCSCompiler` whose `-pipename:` is exactly that id. A server is never stopped while its phase still runs.
- `skip_cross_worktree`: `false` by default. When `true`, a `build`/`test` phase is skipped (outcome `skipped`, `dedupedFrom` = the source record's `ts`, never ship evidence) if a verified, passed record from any worktree of the same repository carries the same `gateKey` within 14 days. The key hashes repository, relative cwd, kind, head, dirty-tree hash, stack, environment hash, the argv with the worktree top replaced by `<root>` plus the content of every argv operand file inside the checkout of at most 1 MB (so a gitignored `.ai-work/ci-local.sh` counts), the nearest `global.json`, the installed SDK list, the resolved tool and the effective profile; labels are excluded. Never for `integration` or `ci` (even with `skip_passed_integration`), never with `--rerun` or `PI_PHASE_NO_SKIP=1`, and never when the tree-state hash caps were exceeded (`pi-phase: tree state too large to hash; not deduplicating`). Legacy records without `gateKey` never match.
- `memory_admission`: absent/`false` (default, off), `true` for defaults, or `{"min_free_percent": 30, "min_swap_free_mb": 500}`. Before a new build/test/integration heavy lease, defer if either threshold is unmet, rechecking each queue poll with a cache lasting at most 5 seconds. macOS uses `memory_pressure -Q` and `sysctl -n vm.swapusage` (at most 1 second per command); Linux reads MemAvailable/MemTotal and SwapFree from `/proc/meminfo`. A macOS swap total of zero disables the swap check. Failed measurements admit with at most one fail-open note per phase. A phase prints once when deferred, e.g. `pi-phase: waiting: memory free 20% < 30%` (or the swap-free threshold). Existing phases are never stopped and CI-only leases are not memory-gated. If no phase of any kind is running, one phase may proceed despite pressure to prevent starvation. Thresholds are nonnegative numbers, with free percentage at most 100; omitted thresholds take their defaults.
  - Optional `integration_burst` inside `memory_admission`, e.g. `{"min_free_percent":30,"min_swap_free_mb":500,"integration_burst":{"slots":2,"min_free_percent":50,"max_load_per_core":1.5,"max_docker_mem_percent":70}}`. Burst is off unless configured; omitted burst fields use the values shown. Effective integration capacity becomes `slots` only when memory free is at least the burst threshold, the five-minute load is at most CPU count × `max_load_per_core`, and summed Docker memory percentages are strictly below `max_docker_mem_percent`. Docker uses `docker stats --no-stream --format '{{.MemPerc}}'`, bounded by 5 seconds and the queue deadline, with results (including failures) cached for at most 30 seconds. Memory shares the five-second admission cache; load is checked each poll. Any missing/failed measurement falls back to configured `integration_slots` (burst is fail-closed). CI-only phases do not run burst probes. Burst slots must be integers 1–32; percentages are 0–100, and the load multiplier is nonnegative.

Memory admission's final decision is inside `claim()` under the existing coordinator, after the tentative permit locks are checked and before waiter removal or lease return. Measurement and process snapshots stay outside the coordinator. Under pressure, the starvation guard checks existing heavy/integration/CI leases, including orphan groups and slots outside a lowered ceiling. Deferral releases every tentative lock, retains the waiter and prints only after unlocking the coordinator. Thus `heavy_slots` remains a hard ceiling; memory can only reduce concurrent admission, without changing priority order or atomic integration claims. With burst configured, `claim()` also counts occupied integration leases outside the current effective range under that same coordinator. When conditions worsen, overflow phases keep their permits, but consume the reduced ceiling: new integration work waits until capacity is genuinely free, even if a lower-numbered permit becomes available. Ordinary build/test work can still use available heavy permits.

A queue wait exceeding 600 seconds prints once: `pi-phase: long queue (Ns): run dev-doctor to look for contention`.

Change this single config for *all cooperating sessions*, not a per-invocation override. Prefer changing limits when idle; lowering them mid-run does not evict current jobs. Do not modify/delete `state/` lock or owner files while jobs are active. Locks are kernel-backed; owner JSON is only diagnostics plus a conservative guard for a crashed supervisor whose child group remains alive. A status entry marked `orphan-group` means a slot remains unavailable until that group goes away; investigate the recorded PID/group rather than deleting state. Crash between launcher creation and metadata publication is guarded by an execution gate: the command never starts until metadata exists. The producer inherits its lease FD. The supervisor starts a new process group, sends TERM then KILL **only to that group** on timeout, cancellation or completed-leader cleanup, and does not kill GitHub CI or other local jobs. Programs deliberately creating new sessions, leaving that group, moving to another user, or escaping inherited descriptors/group tracking cannot be guaranteed; this is not a sandbox. Detached grandchildren can inherit terminal output: they may keep a caller's output pipe open after a crash.

Admission uses one deadline-bounded process-list snapshot per scan outside the shared coordinator; a failed/slow probe conservatively defers admission rather than taking an orphaned permit. Cancellation is checked after admission and before the launcher receives its execution gate, so an already-cancelled command does not start. Execution defaults to **300s** for build/test/integration and **120s** for CI, with a **separate 120s queue budget** (queue time does not consume execution time). Choose ~120s for known short targeted checks; 300s for a build/test phase; execution longer than 600s requires the `--approved-long-timeout` declaration, which the agent adds itself when it has a concrete runtime basis (run such phases in the background, not as a foreground bash call) (e.g. `--timeout 900 --approved-long-timeout`). Long queue waits belong in background jobs (`job_start`): `--queue-timeout` accepts up to 7200s without an approval flag; larger finite queue budgets require `--approved-long-timeout`. Foreground queue waits over 600s still follow wait-guard’s normal long-timeout rules. Do not use speculative long limits. No stdout-silence killer or automatic retries. Exit 77 means withdrawn while queued (command not started; not a failure); 124 means phase timeout; 130/143 mean SIGINT/SIGTERM cancellation; 75 means queue timeout or duplicate CI watcher (neither is a test/CI failure); 125 means wrapper/config/cleanup failure; 126/127 mean command could not be executed; otherwise the exact producer exit (a producer itself can return one of these codes). Timeouts/CI cancellation are **incomplete/unknown**, never a pass or evidence of a remote CI failure. For long-running diagnostics prefer native runner hang support when compatible, not a generic silence timeout.

The default queue timeout remains **120s in every launch mode**, including background jobs. Longer waits require an explicit `--queue-timeout` and belong in the background; the foreground wait-guard is unchanged.

A worktree-lock wait counts as queue time. On queue-timeout exit 75, the command did not start: it is not a failed code/test attempt. Do not loop short requeues: each retry joins the back of the queue. Check `pi-phase status` **once** for running/queued entries and waiter ranks. If a retry is appropriate, retry the phase **once**, in the background (`job_start` if available, otherwise a background agent), with an explicit queue-sized budget, for example `--queue-timeout 2400` (up to 7200 for every kind, no approval flag). This example is not an admission guarantee or a reason to shorten an already larger budget. Add `--priority low` when nothing waits on the result. Continue independent work rather than polling; if that long background wait also times out, report `gate not run: queue saturated`. For a duplicate CI watcher (also 75), reuse the existing watch instead of retrying.

For example, call `job_start` with the following arguments to retry a test phase with a 2400s queue budget while retaining its 300s execution timeout:

```json
{
  "command": "~/.pi/agent/bin/pi-phase run --kind test --label 'unit tests' --timeout 300 --queue-timeout 2400 -- node --test",
  "cwd": "/path/to/repository",
  "timeoutSeconds": 2820
}
```

Preserve your actual phase arguments, command and cwd; the command and label above are generic examples. The outer deadline must cover **queue + execution + cleanup** (here 2400 + 300 + 120 seconds of startup/cleanup allowance). There is no automatic retry or detachment: the caller must launch the background job.

## Iteration profile (`--profile iterate|full`)

`pi-phase run --profile iterate` is an opt-in fast inner loop; the default `full` changes nothing. For a direct `dotnet build` or `dotnet test` argv (through `env`/`nice`; never shell strings or scripts, which run unchanged with a note) it adds `-p:RunAnalyzers=false -p:EnforceCodeStyleInBuild=false` before any `--` runsettings separator, leaving properties you already set alone. Measured: analyzers are about 78% of a Core compile. The ledger records `profile`; it is part of the cross-worktree `gateKey`, so an iterate pass never satisfies a full run; and `pi-train ship` rejects iterate records as Tier 1 evidence (records without `profile` predate it and count as full). Iterate while coding, then run a full-profile Release build of the touched projects before delivery; Tier 1 is unchanged.

## .NET worker lifetime and orchestration guard

For MSBuild-backed `build`, `test`, `publish`, `pack`, `msbuild`, and `restore`, the dotnet shim also injects `-p:UseSharedCompilation=false` and `-nodeReuse:false`. These defaults prevent shared compiler/MSBuild nodes from outliving a phase. Explicit caller properties/node-reuse flags win; `PI_PHASE_SHARED_COMPILATION=1` opts out of the shared-compilation default only (node reuse stays off) without removing the CPU cap. `dotnet run`, metadata commands, assembly-based tests and Microsoft.Testing.Platform tests are unchanged.

In orchestrated sessions only, the `dotnet` guard rejects definite unwrapped `dotnet build|test|publish|pack|msbuild|run` commands and suggests a complete `pi-phase run` replacement (test kind for `test`, build otherwise, with bounded queue/execution timers). Phase-wrapped commands, metadata/tooling/format commands, quoted mentions and uncertain shell syntax remain allowed. `/guards off dotnet` disables the guard through the normal guard registry; ordinary non-orchestrated sessions are unaffected.

`renice-builders` also lowers below-target testhost/vstest.console and `dotnet exec ... MSBuild.dll` workers outside a pi-phase process ancestry. Existing shared compiler/build-server handling is unchanged.

## EPERM after producer success

`Passed!` followed by `Operation not permitted` and exit 125 is a wrapper/cleanup failure, not a passing gate. Keep the full producer log and wrapper diagnostics; inspect `pi-phase status` and the recorded process group once for remaining descendants. Do not delete state, suppress cleanup errors, or infer the producer's exit code from its output. If no owned processes remain, request owner approval for a bounded direct rerun of the exact producer command under `job_start` with a full log and its actual exit code; report that fallback separately from the wrapper failure. Do not bypass the heavy-command wrapper policy without that approval. Do not rerun while descendants remain or ownership is unknown.

Supervisor failures label the primary operation and any secondary cleanup operations with PID/PGID, exception type and errno (without command arguments). A denied group signal also reports `liveness=live` or `liveness=unknown`; unknown remains unsafe. Secondary cleanup faults are recorded before reporting and do not replace the primary exception or skip remaining best-effort finalization. These diagnostic writes are best effort: output failures may hide diagnostics, but do not replace the supervised error or interrupt finalization. This is not a global output guarantee; the preexisting launch-gate close `finally` can still mask an earlier launch error. `producer_exit=N` records an actually observed exit (signals map to 128 + signal), including an unreaped `waitid` observation; `producer_exit=unknown` means no status was obtained. This is separate from `wrapper exit=125`, which remains a failed gate even for producer exit 0. The leader stays unreaped through group signals, and live or unknown groups retain their orphan guard. These diagnostics cannot recover historical producer status.

Each denied cleanup invocation adds at most one supplemental `cleanup_snapshot` (at most two per run: primary and finalization). This read-only `ps` observer requests only PID, PPID, PGID, numeric UID and state; only validated target-group rows are emitted, never arguments, environment, usernames, raw observer output or exception text. It has a one-second timeout, no retries, a 256 KiB accepted-text limit, and at most 32 rows / 8 KiB of diagnostics. Collection uses the OS process table rather than a hard streaming memory cap. Completeness, omitted/malformed counts and observer failures are explicit. Output failures remain best effort and cannot replace the original cleanup error.

`leader_observation=waitid_wnowait` denotes a positively observed unreaped exit; `ps_zombie` is the older-Python fallback and does not establish an exit code. `unknown` means no positive observation. A non-Z leader after a known exit and an actual live descendant (possibly with another UID) remain distinct possibilities, not explanations established by these diagnostics. The supplemental snapshot is non-atomic and may race with exits or omit rows; `absent_at_snapshot` is not historical proof. None of this evidence changes the existing liveness decision, fail-closed handling, signal order or PGID reservation.

For an owner-authorized diagnostic retry of a held cache-only restore, first deploy and verify the diagnostics, confirm current ownership and absence of remaining descendants with bounded value-free checks, and recheck the original disk/growth exception. At most one retry of the original command/cwd/flags is permitted under that original exception, without downloads or policy overrides. Preserve the original failed log; capture the new full wrapper output, producer log, actual wrapper exit and available PID/PGID/run identity separately. Dependent gates remain held. Another 125, live/unknown group or observer failure means stop and return evidence to the owner, not a retry loop or raw-command fallback. A successful retry is new evidence only; the original failure remains failed and historical cause may remain unproven.

The executable `bin/pi-phase` is only a Python launcher; cleanup lives in `pi-phase/pi_phase.py`. It already handles missing groups and ignores EPERM only when no live group members remain. When the first liveness probe still reports live or unknown members, it re-observes up to 5 times at 0.5 s intervals with fresh snapshots, signals only eligible same-user, same-PGID, non-zombie, non-leader members (PGID rechecked before each signal), and succeeds only after a successful probe shows no live members; otherwise the original PermissionError is raised. A reported EPERM alone does not establish that cleanup was safe, so do not swallow all permission errors. Changes to that implementation require separate scope and descendant-cleanup tests.

## Reprioritize a queued phase

```sh
pi-phase reprioritize <pid|label> --priority low|normal|high
pi-phase reprioritize 12345 --priority low
pi-phase reprioritize 'integration checks' --priority normal
```

The target is an exact waiter PID, or an exact label matching exactly one queued waiter owned by your uid. Numeric targets select PIDs. Ambiguous labels are refused with candidate PIDs; another uid's waiters and already-admitted/running phases cannot be changed. There is no force option. `status` shows the updated `priority=`.

The change keeps the waiter's locked inode, token, original enqueue time and sequence: it does not cancel/requeue or reset FIFO position within the new priority class. Existing shortest-expected/aging rules still apply. Queue scans re-read the priority under the coordinator lock; current-version waiters also carry it into running lease metadata and their phase ledger. Lowering high priority immediately frees its queued high slot. Raising to high uses the same approval grant and `max_high` cap as `run --priority high`: without approval nothing changes; at the cap an approved request becomes normal without consuming a grant use. An unchanged priority is a no-op.

No queue-format migration is needed. Older waiters continue to read and rank the updated entry without losing their liveness lock; however, old executables retain their original priority when publishing running metadata/ledger records. For high-priority accounting across admission, use a current-version waiter. The existing phase ledger records the last observed change as `reprioritization` (`previous`, `priority`, `at`, `uid`); the reprioritize command itself writes no ledger line.

## Phase history and throughput

Each `run` appends one version-1 JSON line to `~/.pi/agent/state/pi-phase/ledger/YYYY-MM-DD.jsonl` (UTC), including phases that fail, time out, are cancelled, or are rejected after their kind is known. Ledger files older than 60 days are pruned opportunistically on append. A ledger error prints one stderr note and does not change the phase's output or exit status. There is no service or configuration toggle.

Records contain `v`, `ts`, `session` (`PI_SESSION_ID`, otherwise null), `lane` (`PI_ORCH_ID` then `PI_LANE_ID`, otherwise null), absolute `cwd` (null if the cwd was deleted), `kind`, `stack`, `label`, `priority`, UTC `queuedAt`/`startedAt`/`endedAt`, monotonic `waitS`/`runS`, `exit`, `outcome`, `head`, `dirty`, `argvHash`, `envHash`, and `verified`. `startedAt` is null and `runS` is zero if execution never started; otherwise runtime covers the execution gate through final phase cleanup. `ts` equals `endedAt`. Outcomes are `passed`, `skipped`, `failed`, `queue-timeout`, `timeout`, `cancelled`, `rejected`, `error`, and `withdrawn`; they reflect the cause, not just the numeric exit (a producer exiting 124 is `failed`, not `timeout`). A withdrawn record includes a bounded `withdrawal` object with the requesting `session`, `lane`, `forced` flag and optional `reason`, plus the usual wait telemetry. The withdraw command itself writes no ledger record. A duplicate CI watcher is `rejected`. Internal errors after enqueue but before execution (for example, a failed claim or process launch) are `error`, not `rejected`.

Started phases optionally add `host: {"load1": N}` (1-minute load at execution start, rounded to one decimal). Build/test/integration phases add integer `peakRssMb` (maximum sampled process-tree RSS) and `peakProcRssMb` (maximum sampled single-process RSS). Sampling reuses the ~15-second memory check, including when `rss_cap_mb: 0`; short phases may have zero peaks. These are sampled peaks, not an OS high-water mark.

Nonzero runs optionally add a bounded `failure` object. Classification happens only after completion, reading at most the last 256 KiB of `--log` once. It never changes the exit code, outcome, admission, slots or timeout. Set `failure_categories: false` in config to disable it (default `true`). No log means exit-only classification; unavailable/broken diagnostics omit the object. No log lines or test names enter the ledger. Optional fields are `category`, `detail`, `codes` (up to five unique diagnostic codes, each at most 12 characters), `failedTests`, `log` (path, at most 240 characters), and `offset` (absolute byte offset of the first matched complete log line). A partial first line at the tail boundary is ignored.

Rules, in precedence order:

1. Runner timeout → `timeout` (with `detail: hang` for blame-hang inactivity diagnostics).
2. Exit 76 → `infrastructure`, `detail: rss-cap`; 137/143 → `infrastructure`, `detail: killed`.
3. `--expect-red` → `expected-red`; intentional TDD failure, **not success**. The producer's nonzero exit and `outcome: failed` are preserved.
4. NuGet NU errors, NETSDK1004 or unavailable service index → `restore`.
5. MSB3021/3026/3027/4018/4166, disk full, Docker unavailable, address conflict or OutOfMemoryException → `infrastructure`.
6. Error diagnostic codes → `compile` if any CS/BC/FS/RZ/TS/non-infrastructure MSB code occurs, otherwise `analyzer` (CA/IDE/SA/xUnit/custom analyzer prefixes).
7. Positive VSTest/MTP `Failed: N`, Jest/Vitest `Tests N failed`, or Mocha `N failing` summaries → `assertion`; a crashed test host without an assertion summary → `infrastructure`.
8. Otherwise → `unknown`.

The same single pre-registration history read used for skip-passed also warns about a verified `failed` record with category `compile`, `analyzer` or `assertion` for matching cwd, kind, argvHash, HEAD, non-null dirty state, stack and envHash in the last 14 UTC days. Labels are ignored for this warning. It prints `same state previously failed (<category>); change code before rerunning or inspect the previous log`. This is advisory only: it does not refuse execution, change skip-passed behavior or require a rerun flag; `--rerun` and `PI_PHASE_NO_SKIP=1` still allow the warning.

`stats --failures [--days N] [--kind KIND] [--stack NAME] [--json]` counts failed/timed-out/cancelled records by kind × category (older records count as `unknown`). JSON retains the `days`, `skipped` and `rows` envelope, with `kind`, `category`, `count` in each row. Ordinary `stats` is unchanged. All new fields are optional on version-1 records; old readers continue to work, and complete ledger lines remain under 4096 bytes.

Registered, non-skipped phases add `waitV: 1`, `waitBreakdown` (seconds), `waitScans` (counts), and `waitSamples` (scan count, mean/max 1-minute load, CPU count, minimum cached free-memory percentage, and mean/max busy slots plus capacity per observed pool). Reasons are `slots` (no usable permit), `order` (a usable permit reserved by an earlier waiter), `memory` (memory admission refused while another phase ran), and `other` (before the first scan, coordinator contention, probe failure, or a missing waiter). Memory takes precedence over slots/order. Each failed scan owns the interval until the next scan or admission/end, at roughly 2–2.5-second granularity (`QUEUE_TICK` plus jitter). Skipped, pre-registration rejected and never-registered records omit these fields, as do older records.

Before registration, a Git worktree gets a synchronous snapshot with a total budget of at most 3 seconds, before the queue timer starts. `head` is `git rev-parse HEAD`; `dirty` is `clean` for empty porcelain status, otherwise SHA-256 of `git status --porcelain=v1 -z --untracked-files=normal` bytes, `git diff HEAD --binary` bytes, then each sorted untracked path (NUL-terminated) plus the SHA-256 digest of that file's bytes. Untracked paths come from `git ls-files -o --exclude-standard -z`. At most 2000 untracked files and 200 MB (200,000,000 bytes) total are read; exceeding either limit, an unreadable/changing file, or a timeout makes `dirty` null. Content reads run in a subprocess limited to the remaining snapshot budget, including potentially blocking file I/O. Every Git call uses `--no-optional-locks` and `GIT_OPTIONAL_LOCKS=0`. Outside Git, or on an incomplete snapshot, the existing best-effort daemon snapshot starts after registration (2 seconds for HEAD, 5 seconds combined for dirty state); cleanup waits at most 1 second for it, otherwise the fields stay null. Fallback snapshots are never skip-eligible.

After the child exits and its slots/permits have been released, immediately before writing the ledger, the runner takes another full snapshot with the same 3-second budget and bounds. `verified: true` means HEAD, non-null dirty state and `envHash` were identical at queue time and at the end. Verification does not hold a permit or add to recorded runtime; timeout, null state or a difference leaves `verified: false`. This checks the two endpoints, not intermediate edits: changing files during a run and restoring them before it ends cannot be detected. **Lanes must not edit files while a phase is queued or running.**

`envHash` is SHA-256 of sorted `NAME=value` pairs joined with NUL, for names matching `^(PI_PHASE_|DOTNET_|NUGET_|MSBUILD|NODE_|NPM_|YARN_|VITE_|CONFIGURATION$|ASPNETCORE_|CI$)`. Names containing `TOKEN`, `SECRET`, `PASSWORD` or `KEY` (case-insensitive) are excluded. Only the digest, never environment values, is stored.

For build/test (and integration only with `skip_passed_integration: true`), a `passed` record with `verified: true` in the last 14 UTC calendar days skips queueing and execution only when **realpath cwd, kind, label, argvHash, HEAD, non-null dirty state, stack and envHash** all match. Old records without `verified: true` or a matching `envHash` never qualify. The runner prints the previous pass timestamp, kind, label, short head and runtime, exits 0, and records `outcome: skipped` with `waitS=runS=0` and no start time. `--rerun` bypasses skipping; `PI_PHASE_NO_SKIP=1` disables it globally. CI is never skipped.

The key does **not** cover gitignored files such as `.env` or `appsettings.*.local`, sibling repositories, local package feeds, environment variables outside the listed prefixes, excluded secret-looking environment names, or other external state. Pass **`--rerun`** when any of those inputs changed. The same applies to intermediate edits that were restored before verification.

Privacy: the ledger stores no command arguments, filenames from Git status, or diffs in clear text. `argvHash` is SHA-256 of the command argv joined with NUL. Labels and cwd are still descriptive metadata: do not put secrets in labels. Each line is a single `O_APPEND` write under 4 KiB; exceptionally large session/lane/cwd/label/priority strings are shortened to meet that bound. Reading history never creates state or prunes files.

### Stacks, including frontend commands

Stack is inferred from the command's executable basename: `dotnet` → `dotnet`; `node`, `npm`, `npx`, `yarn`, `pnpm`, `corepack`, `tsc`, `tsgo`, `vite`, `vitest`, `jest`, `playwright`, `eslint`, `prettier`, `turbo`, `nx` → `node`; `python`, `python3`, `pytest` → `python`; `docker`, `docker-compose` → `docker`; `cargo` → `rust`; `go` → `go`; everything else → `other`. Simple `env`, `nice`, `bash -c` and `sh -c` wrappers are unwrapped without executing shell text. Complex shell chains are `other`. Use `run --stack NAME` to override inference, including for scripts; names must match `^[a-z0-9-]{1,20}$`. Older records without a stack are grouped as `other`.

```sh
~/.pi/agent/bin/pi-phase run --kind test --stack node --label 'frontend tests' \
  --timeout 120 --queue-timeout 120 -- npm test
~/.pi/agent/bin/pi-phase stats
~/.pi/agent/bin/pi-phase stats --days 14 --kind test --stack node --json
~/.pi/agent/bin/pi-phase wait --eta --kind build
```

`stats [--days N] [--kind KIND] [--stack NAME] [--json]` defaults to the last 7 UTC calendar days, including today. It groups by day × kind × stack and adds a `total` row per kind × stack across the selected days. Columns are count, started count, wait/run p50 and p90 seconds, queue timeouts, failures, skipped phases, and withdrawn phases (the final `withdrawn` column) (`failed`, `timeout` or `error`, not cancellations or rejections). Wait percentiles include every record; run percentiles include only started records. Percentiles use nearest rank: sorted value at `ceil(p/100 × n)` (one-based); an empty sample is null in JSON, `-` in text. Malformed lines are skipped and counted. JSON is `{ "days": N, "skipped": N, "rows": [...] }`, with each row containing `day`, `kind`, `stack`, `count`, `started`, `waitS`/`runS` objects (`p50`, `p90`), `queueTimeouts`, `skipped`, `failures`, and `withdrawn`. Withdrawn records count in `count` and wait percentiles, not in `failures` or `queueTimeouts`. It reads history only, never live locks.

`wait --eta [--kind KIND] [--expect-fast] [-- COMMAND]` defaults to build and estimates a new normal-priority arrival using the last 7 days' p50 runtime for that kind, running phases' elapsed time, live high/normal waiters, and heavy/integration capacity. Each queued kind uses its own median when available, otherwise the requested kind's median. It models priority/FIFO and integration backfill; low-priority waiters are behind the hypothetical arrival. It does not reserve a place, create a waiter, remove stale files, or mutate locks/permits. With no history it prints `eta unknown (no ledger data)`; otherwise, for example, `eta ~3m (ahead=2 running=4 p50run=160s, basis=18 runs)`. This is an estimate, rounded up to minutes, not an admission promise: memory gates, configuration changes and runtime variation can delay work.

## Memory ceilings (pi-setup#3)

Config keys (defaults in code; `config.json` overrides, `0` turns a key off):

- `rss_cap_mb` (default **12288**; no `DOTNET_GCHeapHardLimit` is set, because it would leak into MSBuild nodes and build servers): while a build/test/integration phase runs, the RSS of its whole process tree (process group plus all descendants) is sampled every ~15 s. If any single process stays above the cap for 3 consecutive samples (~45 s; same pid and start time, a dip or new pid resets it), the phase's process group is stopped and pi-phase exits with the distinct status **76**, printing `rss cap exceeded: pid=… rss=…MB > rss_cap_mb=…MB command=…`. A failed sample never kills. 76 is a pi-phase status like 124/75; it is not a test failure. Statuses: 124 timeout, 125 wrapper/cleanup, 126/127 not executable, 130/143 cancelled, 75 queue timeout/duplicate watcher, **76 RSS cap**, **77 withdrawn**.
- `memory_admission.min_swap_free_mb` code default is now **2048** (was 500; the live `config.json` value is unchanged and still wins). **macOS ignores free swap**: swap files grow on demand, so free swap is always small and produced false alarms (2026-10-22). On macOS admission is decided by `min_free_percent` (`memory_pressure -Q`, the same figure as `kern.memorystatus_level`); the swap floor is enforced on Linux only. The key stays valid on both.
- Memory re-check while running: every ~15 s a low-memory condition prints `warning: … while phase is running (no action taken)` on the runner output (at most every 5 min; no kill). macOS: `kern.memorystatus_level` below 15 %; Linux: swap free below the floor.

Default to no hang dump: `--blame-hang-dump-type none` for VSTest; omit `--hangdump` and its dump-type option for MTP. Use mini (`--blame-hang-dump-type mini` / `--hangdump-type Mini`) only when actively diagnosing a hang, declared with `pi-phase run --diagnose-hang`; read what you need, then delete the dump in the same turn. For direct test/integration argv without `--diagnose-hang`, pi-phase appends `--blame-hang-dump-type none` when `--blame-hang` or `--blame-hang-timeout` has no type, or `--hangdump-type Mini` when `--hangdump` has no type (MTP has no `none`; Mini is its smallest dump). Pass `--diagnose-hang` or any explicit dump type to opt out; shell strings are never rewritten. Otherwise, pi-phase warns before execution when hang/crash dump flags omit a dump type, request full dumps, or request mini without `--diagnose-hang`; injected types do not also warn. The flag silences only mini warnings, not full or missing-type warnings. Inspection treats shell-chain segments separately without executing them; explicit `none` and its own no-dump VSTest preset stay warning-free. After completion it also warns about leftover `.dmp` files ≥ 1 GiB in a bounded cwd scan (depth 6, 20,000 entries, 2 seconds; skipping `node_modules`, `.git`, `obj`, `bin`). Both warnings are advisory, preserve the exit status and never delete files.

## Waiting in the queue

A queued phase is time to use, not to sit in. Run `pi-phase status` once before a heavy phase; when several phases are running or ahead of you, start the phase in the background (`job_start` or a background subagent) and do independent work meanwhile: read code for the next step, write specs, draft PR notes, check issue and PR comments, scope the next issue. A second heavy phase in the same worktree is automatically serialized; do not edit files the queued phase builds (or rerun it afterwards), and never shorten or skip a gate to avoid the queue. With nothing independent to do, end the turn and let the completion notification wake you.

## Worktree lock

Build, test and integration phases serialize within the same realpath git toplevel, across direct, fast and queued policies. Outside git, the key is the realpath cwd. Subdirectories share a lock; linked worktrees and submodules have their own keys. A failed git probe is retried once, then prints a note and locks the cwd instead.

The worktree lock is acquired before global admission: waiting for it holds no global slot or fast permit. A single `--queue-timeout` deadline covers both waits; worktree waiting does not count toward execution or fast-budget timers. Waiters are FIFO and print `waiting for worktree lock (held by <label> pid <pid>)`. A high-priority phase may wait behind a low-priority holder; reprioritize its global queue entry or cancel the holder rather than starting duplicate work.

`--no-worktree-lock` opts out for read-only checks, but is rejected for build (`build writes the worktree`). CI watchers are never locked. `PI_PHASE_WORKTREE_LOCK=0` disables worktree locking for tests or rollback. Lock descriptors remain non-inheritable in the supervisor; producers inherit only the launch gate. Nested phases in the same canonical worktree and state share admission through holder metadata, live slot locks and verified producer ancestry. Environment tokens alone never authorize nesting. Once the holder exits, escaped processes must seek independent admission. This is cooperative admission, not a sandbox against deliberate same-user interference.

Every producer, including nested producers launched in separate sessions, registers its own group before execution. Live or unknown registered groups guard against orphaned work even after a supervisor crash releases its descriptors. Verified-safe cleanup removes only that invocation's group record and clears retired producer PGIDs, preventing recycled PGIDs from guarding completed work. Unsafe and nested producer guards remain intact. Dead records are recovered on the next claim. Dead holders and crashed waiters are recovered automatically; recovery prints `recovered stale worktree lock`. Cancel a waiter with SIGINT/SIGTERM (130/143); a worktree queue timeout returns 75 without starting the command.

Nested registration succeeds only while the parent still owns every slot: releasing a slot that has nested groups, or an independent claimant reserving it, marks the slot record `retired`, and later registrations against it are refused (the nested invocation aborts with exit 125 before launching). The liveness probes behind HIGH-priority counting run before the shared coordinator is taken; unobserved or changed ownership counts as occupied.

**Rollout.** Install by atomic rename (write a temporary file, then `mv` it over the target), never by in-place truncation. Already-running supervisors keep their old in-memory code until they finish, so these safety fixes apply only to supervisors started after the install. The `retired` field is ignored by older readers; newer readers accept its absence, at worst logging one extra stale-recovery warning.

Build/test/integration children default `DOTNET_CLI_USE_MSBUILD_SERVER=0` and `MSBUILDDISABLENODEREUSE=1`, preserving caller overrides. Cleanup drains live, same-user, still-matching group members when group signalling is denied, retains fail-closed handling for unknown groups, and reports drained PIDs. Status marks exited producers with live descendants as draining.

`status` adds `worktree-lock root=... holder=... pid=... kind=... held=...s` and `worktree-wait root=... label=... pid=... kind=... waited=...s` lines (an orphan holder adds `orphan-group`). Ledger fields `worktreeLock`, `worktreeWaitS` and `worktreeRoot` describe worktree admission separately from the global `waitS` and ETA inputs. `withdraw` does not see worktree waiters: cancel them instead. `wait --eta` ignores the worktree lock.

## Withdrawing a queued phase

```sh
pi-phase withdraw [ID] [--label LABEL] [--mine] [--all] [--force] [--reason TEXT]
pi-phase withdraw abcdef123456 --reason 'already covered elsewhere'
pi-phase withdraw --mine --all
```

At least one selector is required: `ID` is a hex token prefix of at least 6 characters (status and queued heartbeats show 12), `--label` matches an exact label, and `--mine` selects your session or lane. Selectors are ANDed. Multiple matches require `--all`; otherwise nothing is withdrawn. `--mine` requires an identity environment variable.

Ownership means the same `PI_SESSION_ID`, or the same lane (`PI_ORCH_ID`, then `PI_LANE_ID`). Withdrawing another session/lane's waiter requires `--force --reason TEXT`; the reason must be 1–120 printable characters with no control characters. Refusals are all-or-nothing, even with `--all`. Forced withdrawals record `forced: true`.

The withdraw command exits **0** on success, **1** for no queued match (including already-admitted phases), **2** for usage errors or ambiguous matches, and **3** for ownership or old-version refusal. A successfully withdrawn waiter exits **77** within about 3 seconds, without starting its command. Its queue entry disappears immediately, atomically with admission.

Running or already-admitted phases are never touched: use SIGINT/SIGTERM cancellation instead. `direct` and `ci` phases have no queue entry and cannot be withdrawn. Waiters started by an older pi-phase are refused, even with `--force`; cancel their process instead. Older pi-phase `stats` readers count `withdrawn` ledger lines as malformed.
