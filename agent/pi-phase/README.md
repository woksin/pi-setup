# Local pi phase runner

`~/.pi/agent/bin/pi-phase` is an **explicit**, foreground, cooperative wrapper for heavy commands run by this user's pi sessions and subagents on this host. It does not change shell tools or start a daemon. Adopt it for builds, tests, integration runs and local CI watching; ordinary `bash` and pre-existing jobs bypass it. It is not host-wide enforcement for other users or programs.

```sh
~/.pi/agent/bin/pi-phase run --kind build --label 'solution Release' \
  --timeout 300 --queue-timeout 120 -- dotnet build My.sln -c Release -m:2
~/.pi/agent/bin/pi-phase run --kind test --label 'unit tests' \
  --timeout 300 --queue-timeout 120 -- dotnet test Tests.csproj -c Release --no-build
~/.pi/agent/bin/pi-phase status
```

Use a single *direct executable and its arguments* after `--` for each phase. Do not hide phases in shell chains/pipelines or use `| head/grep` as gate evidence; the runner streams raw output and returns the **producer's exact exit code**. One command per phase. `-m:2` above is an **explicit example**, not a silently imposed MSBuild option: choose the project's correct configuration/CI flags and parallelism yourself. Run status in a separate terminal to see kind, label, PID, cwd and elapsed time (never full command or arguments); queued/running heartbeat messages appear on the initiating terminal every ~5 seconds. A noninteractive caller must keep the foreground process running until completion. If `job_start` (pi-jobs) exists, prefer it for completion notification/cancellation; otherwise run a single bounded `bash` tool call. Set the *outer caller's* timeout greater than **queue-timeout + phase timeout + ~5 seconds cleanup/startup**, so the caller does not kill the supervisor prematurely. Do not use repeated polling as an alternative.

## Compact output with a full log

Prefer `--log FILE` over shell redirects or output pipes: it overwrites FILE (creating parent directories) with the producer's full, combined stdout/stderr without streaming it to the terminal. Runner status and heartbeats remain visible. On completion, including timeout, cancellation or queue timeout, it prints the last 60 log lines followed by `pi-phase: log=<absolute path> exit=<code> lines=<count>`. The exit status is unchanged; read the full log separately when diagnosing a failure.

```sh
~/.pi/agent/bin/pi-phase run --kind test --label 'unit tests' \
  --timeout 300 --queue-timeout 120 --log .ai-work/unit-tests.log --tail 20 \
  -- dotnet test Tests.csproj -c Release --no-build
```

`--tail N` requires `--log` and a nonnegative integer; `--tail 0` prints only runner messages and the summary. Without `--log`, output and exit behaviour are unchanged.

## Capacity and timeouts

The shipped config sets heavy capacity **4** (build/test/integration); without a config file the fallback is **2**. Integration additionally occupies **1** integration permit (atomic claim, no deadlock). CI watchers take **no heavy permits**. Config is shared in `~/.pi/agent/pi-phase/config.json`, optional, for example:

```json
{"heavy_slots": 2, "integration_slots": 1}
```

### Optional performance flags

Config also accepts these keys (unknown keys are ignored and invalid values fall back to defaults, with a note, deduplicated per phase):

- `msbuild_max_cpu`: `0` (default, off), a positive integer, or `"auto"` = `max(2, (os.cpu_count() or 1) // heavy_slots)`. For build/test/integration, an executable phase-private POSIX `dotnet` shim is prepended to the child's PATH, including calls inside scripts. It finds the real executable on the original PATH, excluding the shim directory, and inserts `-m:N` immediately after the first non-option subcommand when it is `build`, `test`, `publish`, `pack`, `msbuild` or `restore`. Arguments matching `-m`, `-m:*`, `/m`, `/m:*`, `-maxcpucount*`, `/maxcpucount*` or `--maxcpucount*` (case-insensitive) disable insertion. Absolute dotnet executable paths bypass PATH and thus the cap. For `dotnet test`, assembly arguments ending in `.dll`/`.exe` bypass insertion, as does a nearest `global.json` selecting `test.runner = "Microsoft.Testing.Platform"`. The nearest config is resolved from each invocation's cwd; an unreadable/invalid runner config also leaves arguments untouched. If the shim cannot be prepared, the phase runs uncapped with one note. Startup reports a successfully installed cap; no MSBuild response files are changed.
- `container_test_detection`: `"off"`, `"hint"` (default), or `"promote"`. Test phases probe Docker no more often than every 15 seconds, with a 5-second subprocess timeout in a daemon thread that never delays or kills the phase. The first container labelled `org.testcontainers=true` created after phase start produces one integration/filter hint. Only a phase that was the sole running test/integration phase throughout the observation interval records a SHA-1 fingerprint of the real cwd and command in `state/container-tests.json`. Missing/failing Docker is ignored. `"promote"` also makes a later matching test phase atomically claim both a heavy slot and an integration permit using the existing integration admission order. A start-generation marker remembers peers that start and finish between Docker polls. Attribution is conservative: even a peer starting after container creation but before the poll suppresses recording. Other, non-pi-phase Docker activity cannot be attributed; promotion is opt-in. To forget observations while phases are idle, remove `state/container-tests.json`.
- `cold_worktree_hint`: `true` (default). Build/test phases in a Git worktree (`.git` file) without an `obj` directory within depth 3 suggest reusing a warm lane worktree. The scan skips `.git`, `node_modules` and symlinks and stops after 1000 entries; incomplete scans produce no hint. Message only.
- `phase_nice`: `0` (default, off) or an integer 1–19. Build, test and integration producers start at that Unix nice level (a caller that is already nicer keeps its level). Children inherit it, including a compiler server (VBCSCompiler) or MSBuild nodes a phase starts, so Docker, agents and health checks keep CPU when compiles saturate the host. CI watchers are unaffected. Running phases keep their priority after a config change.
- `memory_admission`: absent/`false` (default, off), `true` for defaults, or `{"min_free_percent": 30, "min_swap_free_mb": 500}`. Before a new build/test/integration heavy lease, defer if either threshold is unmet, rechecking each queue poll with a cache lasting at most 5 seconds. macOS uses `memory_pressure -Q` and `sysctl -n vm.swapusage` (at most 1 second per command); Linux reads MemAvailable/MemTotal and SwapFree from `/proc/meminfo`. A macOS swap total of zero disables the swap check. Failed measurements admit with at most one fail-open note per phase. A phase prints once when deferred, e.g. `pi-phase: waiting: memory free 20% < 30%` (or the swap-free threshold). Existing phases are never stopped and CI-only leases are not memory-gated. If no phase of any kind is running, one phase may proceed despite pressure to prevent starvation. Thresholds are nonnegative numbers, with free percentage at most 100; omitted thresholds take their defaults.
  - Optional `integration_burst` inside `memory_admission`, e.g. `{"min_free_percent":30,"min_swap_free_mb":500,"integration_burst":{"slots":2,"min_free_percent":50,"max_load_per_core":1.5,"max_docker_mem_percent":70}}`. Burst is off unless configured; omitted burst fields use the values shown. Effective integration capacity becomes `slots` only when memory free is at least the burst threshold, the five-minute load is at most CPU count × `max_load_per_core`, and summed Docker memory percentages are strictly below `max_docker_mem_percent`. Docker uses `docker stats --no-stream --format '{{.MemPerc}}'`, bounded by 5 seconds and the queue deadline, with results (including failures) cached for at most 30 seconds. Memory shares the five-second admission cache; load is checked each poll. Any missing/failed measurement falls back to configured `integration_slots` (burst is fail-closed). CI-only phases do not run burst probes. Burst slots must be integers 1–32; percentages are 0–100, and the load multiplier is nonnegative.

Memory admission's final decision is inside `claim()` under the existing coordinator, after the tentative permit locks are checked and before waiter removal or lease return. Measurement and process snapshots stay outside the coordinator. Under pressure, the starvation guard checks existing heavy/integration/CI leases, including orphan groups and slots outside a lowered ceiling. Deferral releases every tentative lock, retains the waiter and prints only after unlocking the coordinator. Thus `heavy_slots` remains a hard ceiling; memory can only reduce concurrent admission, without changing priority order or atomic integration claims. With burst configured, `claim()` also counts occupied integration leases outside the current effective range under that same coordinator. When conditions worsen, overflow phases keep their permits, but consume the reduced ceiling: new integration work waits until capacity is genuinely free, even if a lower-numbered permit becomes available. Ordinary build/test work can still use available heavy permits.

A queue wait exceeding 600 seconds prints once: `pi-phase: long queue (Ns): run dev-doctor to look for contention`.

Change this single config for *all cooperating sessions*, not a per-invocation override. Prefer changing limits when idle; lowering them mid-run does not evict current jobs. Do not modify/delete `state/` lock or owner files while jobs are active. Locks are kernel-backed; owner JSON is only diagnostics plus a conservative guard for a crashed supervisor whose child group remains alive. A status entry marked `orphan-group` means a slot remains unavailable until that group goes away; investigate the recorded PID/group rather than deleting state. Crash between launcher creation and metadata publication is guarded by an execution gate: the command never starts until metadata exists. The producer inherits its lease FD. The supervisor starts a new process group, sends TERM then KILL **only to that group** on timeout, cancellation or completed-leader cleanup, and does not kill GitHub CI or other local jobs. Programs deliberately creating new sessions, leaving that group, moving to another user, or escaping inherited descriptors/group tracking cannot be guaranteed; this is not a sandbox. Detached grandchildren can inherit terminal output: they may keep a caller's output pipe open after a crash.

Admission uses one deadline-bounded process-list snapshot per scan outside the shared coordinator; a failed/slow probe conservatively defers admission rather than taking an orphaned permit. Cancellation is checked after admission and before the launcher receives its execution gate, so an already-cancelled command does not start. Execution defaults to **300s** for build/test/integration and **120s** for CI, with a **separate 120s queue budget** (queue time does not consume execution time). Choose ~120s for known short targeted checks; 300s for a build/test phase; longer than 600s for either budget requires the `--approved-long-timeout` declaration, which the agent adds itself when it has a concrete runtime basis (run such phases in the background, not as a foreground bash call) (e.g. `--timeout 900 --approved-long-timeout`). Do not use speculative long limits. No stdout-silence killer or automatic retries. Exit 124 means phase timeout; 130/143 mean SIGINT/SIGTERM cancellation; 75 means queue timeout or duplicate CI watcher (neither is a test/CI failure); 125 means wrapper/config/cleanup failure; 126/127 mean command could not be executed; otherwise the exact producer exit (a producer itself can return one of these codes). Timeouts/CI cancellation are **incomplete/unknown**, never a pass or evidence of a remote CI failure. For long-running diagnostics prefer native runner hang support when compatible, not a generic silence timeout.

On queue-timeout exit 75, the command did not start: it is not a failed code/test attempt. Do not loop short requeues: each retry joins the back of the queue. Continue code work and retry the phase **once**, in the background (`job_start`), with a queue budget sized to the queue: `pi-phase status` showing several phases running or queued ahead is the concrete basis for `--queue-timeout 3600 --approved-long-timeout` (up to 7200 for integration). Add `--priority low` when nothing waits on the result. If that long wait also times out, report `gate not run: queue saturated`. The timeout message does not include counts or rank: run `pi-phase status` once at that checkpoint for running/queued entries and waiter ranks. For a duplicate CI watcher (also 75), reuse the existing watch instead of retrying.

## .NET worker lifetime and orchestration guard

For MSBuild-backed `build`, `test`, `publish`, `pack`, `msbuild`, and `restore`, the dotnet shim also injects `-p:UseSharedCompilation=false` and `-nodeReuse:false`. These defaults prevent shared compiler/MSBuild nodes from outliving a phase. Explicit caller properties/node-reuse flags win; `PI_PHASE_SHARED_COMPILATION=1` opts out of both lifetime defaults without removing the CPU cap. `dotnet run`, metadata commands, assembly-based tests and Microsoft.Testing.Platform tests are unchanged.

In orchestrated sessions only, the `dotnet` guard rejects definite unwrapped `dotnet build|test|publish|pack|msbuild|run` commands and suggests a complete `pi-phase run` replacement (test kind for `test`, build otherwise, with bounded queue/execution timers). Phase-wrapped commands, metadata/tooling/format commands, quoted mentions and uncertain shell syntax remain allowed. `/guards off dotnet` disables the guard through the normal guard registry; ordinary non-orchestrated sessions are unaffected.

`renice-builders` also lowers below-target testhost/vstest.console and `dotnet exec ... MSBuild.dll` workers outside a pi-phase process ancestry. Existing shared compiler/build-server handling is unchanged.

## EPERM after producer success

`Passed!` followed by `Operation not permitted` and exit 125 is a wrapper/cleanup failure, not a passing gate. Keep the full producer log and wrapper diagnostics; inspect `pi-phase status` and the recorded process group once for remaining descendants. Do not delete state, suppress cleanup errors, or infer the producer's exit code from its output. If no owned processes remain, request owner approval for a bounded direct rerun of the exact producer command under `job_start` with a full log and its actual exit code; report that fallback separately from the wrapper failure. Do not bypass the heavy-command wrapper policy without that approval. Do not rerun while descendants remain or ownership is unknown.

The executable `bin/pi-phase` is only a Python launcher; cleanup lives in `pi-phase/pi_phase.py`. It already handles missing groups and ignores EPERM only when no live group members remain. A reported EPERM alone does not establish that cleanup was safe, so do not swallow all permission errors. Changes to that implementation require separate scope and descendant-cleanup tests.

## Phase history and throughput

Each `run` appends one version-1 JSON line to `~/.pi/agent/state/pi-phase/ledger/YYYY-MM-DD.jsonl` (UTC), including phases that fail, time out, are cancelled, or are rejected after their kind is known. Ledger files older than 60 days are pruned opportunistically on append. A ledger error prints one stderr note and does not change the phase's output or exit status. There is no service or configuration toggle.

Records contain `v`, `ts`, `session` (`PI_SESSION_ID`, otherwise null), `lane` (`PI_ORCH_ID` then `PI_LANE_ID`, otherwise null), absolute `cwd` (null if the cwd was deleted), `kind`, `stack`, `label`, `priority`, UTC `queuedAt`/`startedAt`/`endedAt`, monotonic `waitS`/`runS`, `exit`, `outcome`, `head`, `dirty`, and `argvHash`. `startedAt` is null and `runS` is zero if execution never started; otherwise runtime covers the execution gate through final phase cleanup. `ts` equals `endedAt`. Outcomes are `passed`, `failed`, `queue-timeout`, `timeout`, `cancelled`, `rejected`, and `error`; they reflect the cause, not just the numeric exit (a producer exiting 124 is `failed`, not `timeout`). A duplicate CI watcher is `rejected`. Internal errors after enqueue but before execution (for example, a failed claim or process launch) are `error`, not `rejected`.

`head` is `git rev-parse HEAD` (2-second probe). `dirty` is `clean` for empty porcelain status, otherwise SHA-256 of `git status --porcelain=v1 -z --untracked-files=normal` bytes followed by `git diff HEAD --binary` bytes (5-second combined budget). Every Git call uses `--no-optional-locks` and `GIT_OPTIONAL_LOCKS=0` to prevent optional index locking. Failed probes, including non-Git cwd, yield null. Exactly one snapshot is started in a daemon thread immediately after waiter registration: queueing and admission never wait for Git, and no admission-time snapshot is taken. After phase cleanup and permit release, the ledger waits at most 1 second for the result; if it is still running, both `head` and `dirty` are null. These fields describe the code state when the phase was queued, not its state at completion. **Lanes must not edit files while a phase is queued or running.**

Privacy: the ledger stores no command arguments, filenames from Git status, or diffs in clear text. `argvHash` is SHA-256 of the command argv joined with NUL. Labels and cwd are still descriptive metadata: do not put secrets in labels. Each line is a single `O_APPEND` write under 4 KiB; exceptionally large session/lane/cwd/label/priority strings are shortened to meet that bound. Reading history never creates state or prunes files.

### Stacks, including frontend commands

Stack is inferred from the command's executable basename: `dotnet` → `dotnet`; `node`, `npm`, `npx`, `yarn`, `pnpm`, `corepack`, `tsc`, `tsgo`, `vite`, `vitest`, `jest`, `playwright`, `eslint`, `prettier`, `turbo`, `nx` → `node`; `python`, `python3`, `pytest` → `python`; `docker`, `docker-compose` → `docker`; `cargo` → `rust`; `go` → `go`; everything else → `other`. Simple `env`, `nice`, `bash -c` and `sh -c` wrappers are unwrapped without executing shell text. Complex shell chains are `other`. Use `run --stack NAME` to override inference, including for scripts; names must match `^[a-z0-9-]{1,20}$`. Older records without a stack are grouped as `other`.

```sh
~/.pi/agent/bin/pi-phase run --kind test --stack node --label 'frontend tests' \
  --timeout 120 --queue-timeout 120 -- npm test
~/.pi/agent/bin/pi-phase stats
~/.pi/agent/bin/pi-phase stats --days 14 --kind test --stack node --json
~/.pi/agent/bin/pi-phase wait --eta --kind build
```

`stats [--days N] [--kind KIND] [--stack NAME] [--json]` defaults to the last 7 UTC calendar days, including today. It groups by day × kind × stack and adds a `total` row per kind × stack across the selected days. Columns are count, started count, wait/run p50 and p90 seconds, queue timeouts, and failures (`failed`, `timeout` or `error`, not cancellations or rejections). Wait percentiles include every record; run percentiles include only started records. Percentiles use nearest rank: sorted value at `ceil(p/100 × n)` (one-based); an empty sample is null in JSON, `-` in text. Malformed lines are skipped and counted. JSON is `{ "days": N, "skipped": N, "rows": [...] }`, with each row containing `day`, `kind`, `stack`, `count`, `started`, `waitS`/`runS` objects (`p50`, `p90`), `queueTimeouts`, and `failures`. It reads history only, never live locks.

`wait --eta [--kind KIND]` defaults to build and estimates a new normal-priority arrival using the last 7 days' p50 runtime for that kind, running phases' elapsed time, live high/normal waiters, and heavy/integration capacity. Each queued kind uses its own median when available, otherwise the requested kind's median. It models priority/FIFO and integration backfill; low-priority waiters are behind the hypothetical arrival. It does not reserve a place, create a waiter, remove stale files, or mutate locks/permits. With no history it prints `eta unknown (no ledger data)`; otherwise, for example, `eta ~3m (ahead=2 running=4 p50run=160s, basis=18 runs)`. This is an estimate, rounded up to minutes, not an admission promise: memory gates, configuration changes and runtime variation can delay work.

## Memory ceilings (pi-setup#3)

Config keys (defaults in code; `config.json` overrides, `0` turns a key off):

- `rss_cap_mb` (default **12288**; no `DOTNET_GCHeapHardLimit` is set, because it would leak into MSBuild nodes and build servers): while a build/test/integration phase runs, the RSS of its whole process tree (process group plus all descendants) is sampled every ~15 s. If any single process stays above the cap for 3 consecutive samples (~45 s; same pid and start time, a dip or new pid resets it), the phase's process group is stopped and pi-phase exits with the distinct status **76**, printing `rss cap exceeded: pid=… rss=…MB > rss_cap_mb=…MB command=…`. A failed sample never kills. 76 is a pi-phase status like 124/75; it is not a test failure. Statuses: 124 timeout, 125 wrapper/cleanup, 126/127 not executable, 130/143 cancelled, 75 queue timeout/duplicate watcher, **76 RSS cap**.
- `memory_admission.min_swap_free_mb` code default is now **2048** (was 500; the live `config.json` value is unchanged and still wins). **macOS ignores free swap**: swap files grow on demand, so free swap is always small and produced false alarms (2026-10-22). On macOS admission is decided by `min_free_percent` (`memory_pressure -Q`, the same figure as `kern.memorystatus_level`); the swap floor is enforced on Linux only. The key stays valid on both.
- Memory re-check while running: every ~15 s a low-memory condition prints `warning: … while phase is running (no action taken)` on the runner output (at most every 5 min; no kill). macOS: `kern.memorystatus_level` below 15 %; Linux: swap free below the floor.

## Waiting in the queue

A queued phase is time to use, not to sit in. Run `pi-phase status` once before a heavy phase; when several phases are running or ahead of you, start the phase in the background (`job_start` or a background subagent) and do independent work meanwhile: read code for the next step, write specs, draft PR notes, check issue and PR comments, scope the next issue. Do not start a second heavy phase in the same worktree, do not edit files the queued phase builds (or rerun it afterwards), and never shorten or skip a gate to avoid the queue. With nothing independent to do, end the turn and let the completion notification wake you.
